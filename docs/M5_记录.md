## 三、修掉一个测试污染（本轮发现，含我自己的一个错）

**现象**：service 测试把请求写进了仓库的 `logs/usage.jsonl`（252 行测试记录），
而 `/metrics` 的今日成本正是从该文件回填的——**测试噪声会被算成真实花费**
（容器首次启动就显示 `cost_cny_today = 2.0`）。

**修法**：在既有的 `tests/conftest.py`（M0 起就有 `src` 路径引导）里新增一个
autouse 夹具，把 `LOG_DIR` / `USAGE_LOG` 重定向到临时目录。
**验证**：跑测试前后 `logs/usage.jsonl` 行数 `253 → 253`。
被污染的旧日志改名为 `logs/usage.jsonl.pretest-backup-20261012`（保留未删）。

**期间我自己踩的坑**：改写 `conftest.py` 时把原有的 `src` 路径引导整段删掉了，
导致全部测试 `ModuleNotFoundError`。根因是"以为这文件是我新建的"，
没先 `git log -- tests/conftest.py` 确认它的来历。已恢复，并写成幂等插入。
教训：**改一个我没确认过来历的文件之前，先查它在版本库里的历史**。

## 五、Docker Desktop 环境故障的排查（非项目代码问题）

1. 10-11 两次启动后 `docker info` 都失败（pipe 不存在）；查到
   `%LOCALAPPDATA%\Docker\backend.error.json`（10-08 留下）显示 **Secrets Engine 初始化失败**：
   把 `engine.sock` 重命名为 `.stale` 时报 1920（The file cannot be accessed by the system）。
2. `engine.sock` 属性为 `Archive + ReparsePoint + Encrypted`（EFS）。
   `fsutil reparsepoint delete`、`Move-Item`、`cipher /d` 全部失败（1920 / 拒绝访问）；
   结论：那是**陈旧且不可访问的残影文件**，本机权限层动不了它。
   容器内也看不到该文件，无法代为删除。
3. 10-12 重新启动 Docker Desktop 并**多等了一会儿**（此前只等约 60 秒）→ 引擎就绪
   （Server 29.8.0），`backend.error.json` 自行消失；旧 `engine.sock` 仍在，但不再阻塞启动。
   **结论：上次没起来是等待不足 + 陈旧文件叠加，没有做任何系统级清理、没有重装。**
4. **一次误判，已纠正**：排查时我用 `New-Item` 在
   `%LOCALAPPDATA%\docker-secrets-engine\` 下建过一个 0 字节测试文件，
   随后一直以为它落在真实磁盘上、需要手动删除（因为我在沙箱里删不掉）。
   两次让用户手动删除都报"路径不存在"，于是换**沙箱外**的视角复核：

   ```
   docker run --rm -v "%LOCALAPPDATA%\docker-secrets-engine:/mnt/s:ro" \
     analytics-copilot:m5-1 sh -c "ls -la /mnt/s; test -e /mnt/s/codex-write-test.txt && echo EXISTS || echo NOT_FOUND"
   → 只有 engine.sock；NOT_FOUND
   ```

   结论：那个文件**只存在于我这边的沙箱视图**——该目录的 ACL 只给沙箱身份 `RX`，
   我的写入被重定向到了沙箱侧，真实磁盘上从未出现。**用户无需做任何清理。**
   （同一次复核也确认：仓库改动与 Downloads 里的台账写入都落在真实磁盘上。）

   教训：**跨权限边界判断"文件是否存在"时，不能只用自己进程的视角**；
   可以用一个跑在边界之外的中立观察者（这里是 Docker 守护进程侧的挂载视图）交叉验证。

## 九、兜底回答的可用性修订（2026-10-12，用户手机实测反馈）

### 9.1 现象（用户反馈）

手机问「最近三个月为什么销售额下降，按国家」时，页面上只有一句
`本次只做事实与相关变化描述：最大维度是 United Kingdom（值 8187806.36）`，
边界说明压过了信息量——**降级回答只说"我不能做什么"，没有把已经查到的结果讲清楚，
也没告诉用户下一步能问什么**。

### 9.2 根因（两条，机制层面查实）

1. **兜底只取一格结果**：`_causal_fallback` 只用"维度贡献"的第一行拼一句话，
   而趋势结果、维度占比这些已经执行完的数据没被组织成结论；
   兜底路径还**绕过了验证层**（claims 为空），等于免检。
2. **口径没写明白**：`understanding.time_window` 对「最近三个月」只解析出「最近」，
   而且 `plan()` **完全没用时间窗**（规则计划的 SQL 没有时间过滤）。
   所以那句 UK 8187806.36 是**全期**数字，用户问的却是"最近三个月"——
   数字没错，**口径没对上，且没有声明**。

### 9.3 本轮改了什么

| 改动 | 内容 |
|---|---|
| 事实化 | 兜底改为从结果行机械生成 2 条事实：①按月趋势（首/末/最低/最高月）②占比最高的三个维度；数字逐字取自结果并声明来源步骤 |
| 走验证层 | 兜底结论进同一套 V1/V2/V3/V4，`verification.status` 如实返回（此前是"免检"） |
| 口径声明 | 显式写出"以上为全期汇总，规则计划当前不按最近 N 个月过滤时间窗" |
| 末月提醒 | 数据集最后一个月只到 `2011-12-09`，属不完整月；命中时自动加提醒，避免把 12 月的低值读成暴跌 |
| 下一步 | 返回 `next_questions`（确定性模板，不调模型），页面渲染成"可以继续问" |

### 9.5 后续修复清单（待授权，先记录不动手）

来源：用户在手机实测后提出的三条，加上本轮实测复核的结论。

#### P0-1 时间窗未生效（**已修复，2026-10-12**）

**原缺陷**：`understand('最近三个月销售额为什么下降')` → `time_window='最近'`（"三个月"丢失），
且 `plan()` 的 SQL 无任何时间过滤；公网实测答案就是全期（2010-12 ~ 2011-12）数字。
性质是**理解 + 规划失败**，不是设计取舍。

**修法**：新增 `src/analytics_copilot/window.py`，把时间窗解析成**一个**对象，
SQL、答案口径、caveat 三者同源：

```json
{"requested":"最近三个月","anchor":"dataset_max_date",
 "anchor_value":"2011-12-09 12:50:00","unit":"month","n":3,
 "resolved_range":["2011-10-01","2011-12-09"],
 "complete_period":false,"applied":true}
```

三条约束都落进了代码：

1. **锚点 = 数据集最后一天**（`metadata.profile.ts_max`），不是今天；
2. **只有明确的"N 个月/周/天"才生效**；只有"最近"两个字时不猜（`applied=false`，
   口径按全期如实声明）——`最近哪个国家的销售额下降最多` 因此不会被误过滤；
3. **口径必须可见**：规则路径与 LLM 路径都写入答案；LLM 路径另加机械检查——
   计划里没有 `invoice_ts` 过滤时如实说明"没有按时间窗过滤，结果覆盖全期"。

**公网实测（同一问题，修复前后）**：

| | 结论首句 | 口径说明 |
|---|---|---|
| 修复前 | 从 **2010-12** 的 748957.02 到 2011-12 的 433668.01 | "以上事实为全期汇总，规则计划当前不按最近 N 个月过滤" |
| 修复后 | 从 **2011-10** 的 1070704.67 到 2011-12 的 433668.01 | "最近三个月，按数据集最后一天 2011-12-09 为锚点解析为 2011-10-01 ~ 2011-12-09，末月不完整" |

维度占比也随之变成窗口内口径（DOT 2.5% / 23084 1.9% / 22086 1.5%，此前是全期口径）。
接口新增 `time_window` 字段，前端与复核者都能直接读到这次用的口径。

**验收**：`pytest` 70 passed（新增 `tests/test_window.py` 5 条 + 时间窗行为 3 条），
`ruff` 通过；`最近哪个国家的销售额下降最多` 仍走全期对比（有回归测试守着）。

#### P0-2 假设显式化（**已修复，2026-10-12**）

**原判断修正**：`understand('为什么销售额下降？')` 本来就返回
`missing=['分析维度（按国家、商品还是客户看？）']` → 澄清机制本来就有；
`商品最近三个月…` 命中词表 → `dims=['stock_code']`。真正缺的是**默认可见性**。

**修法**（原则：**不禁止默认，只禁止隐藏默认**）：新增 `analysis_context()`，
输出结构化字段 + 一句可展示文案，并把它放在结论之前：

```
分析口径：指标=销售额；维度=国家（未指定，按默认）；时间范围=全期（2010-12-01 ~ 2011-12-09）；
          可指定维度：国家 / 商品 / 客户
```

`dimension_source` 区分"问题中指定"与"未指定，按默认"——**只有真的默认了才写默认**，
所以点名商品的问法不会出现"默认"字样。接口新增 `analysis_context` 字段。

**三条验收用例（用户指定，公网实测 + 单元测试）**：

| 用例 | 期望 | 结果 |
|---|---|---|
| `销售额怎么样` | 必须出现"按默认" | ✅ `维度=国家（未指定，按默认）` |
| `哪个商品销售额最高` | 必须是"商品"，不得出现"默认国家" | ✅ `维度=商品（问题中指定）` |
| `哪个下降最多？` | 不许偷偷选，先澄清 | ✅ 抛 `ClarifyNeeded`，缺项含"分析维度" |

边界：**能补充事实，不替用户决定分析范围**——默认可以存在，但必须写在脸上。

#### P1-1 降级答案排序 + 商品语义（**已修复，2026-10-12**）

**排序**：兜底回答改成 **①先说不能回答什么 ②再给替代分析 ③再给限制 ④最后给下一步**。
现在的第一句是「当前不能判断"为什么"的原因（本项目不做因果推断）。基于现有数据可以确认：…」。

**商品语义（新发现，原判断需要修正）**：数据里**本来就有** `description` 字段
（在只读视图 `v_sales` / `v_returns` 里），所以"数据未提供商品名称"是错的。
真正的问题是计划没用它，于是出现「商品 DOT」这种把编码当商品名的说法——
而 `DOT` 的描述是 **DOTCOM POSTAGE（邮费）**，根本不是商品。修法：

- 规则计划在 `stock_code` 维度上追加 `MAX(description) AS description`；
- 结论句里带上描述（`DOT（DOTCOM POSTAGE）`），并提醒"编码 + 原始描述（未清洗，
  可能是邮费/费用/残次品）"；
- LLM 路径加了机械检查：计划用 `stock_code` 却没带 `description` → 明确说明"无法确认对应什么商品"。
- 进结论句的描述会**去掉其中的数字**（如 `4 PURPLE FLOCK…` 的数量前缀），
  否则 V1 会把描述里的数字当成"没有来源的数据断言"而误判正确结论；原始描述在证据表里原样可见。

**另外补的两条机械提醒**：

- **维度高度分散**：第一名占比 < 50% 时提示"不能当作主要因素
  （「谁贡献最大」与「谁变化最大」是两件事）"——兜底路径此前漏了这条；
- **「下降最多」≠「贡献最大」**：问题含"下降/跌幅 + 最多/最大"时说明
  "指单条记录降幅最大，不等于对整体销售额的贡献最大（后者看绝对金额损失）"。

**顺带查实一个会挡主路径的已知限制**：纯数字商品编码（`23084`）会被验证层 V1
当成"数据断言数字"，导致正确结论被判不可信（这正是 `holdout_hard` 里的 HO-HARD-05）。
本轮**没有改冻结的验证规则**，只在兜底路径把编码如实声明为"来自该步骤结果"，
使这条路径重新判为 `supported`。**LLM 路径仍会受影响**——根治要把"裸编号"从数字断言里
剔除，属 v1.2 任务，建议优先做（下面"已登记"里升级优先级）。

#### P1-2 数据能力卡（Data Capability Card）

- 认可，且便宜：`metadata.json` 已有 `profile` / `caliber` / `allowed_views`，扩几个字段即可。
- 用途限定为两条：**①入口展示（页面 + 首页说明）②拒答时引用依据**。
- **不做**"每题所需能力 vs 当前能力"的实时比对——那会退化成规则引擎，收益低。

#### 已登记但优先级低

1. 末月不完整目前只在兜底路径提醒，LLM 正常路径还没有这条检查（该进验证层）；
2. 兜底触发依赖"模型拒答理由里含因果词"，措辞不同会掉回普通拒答
   （本轮 T-203「哪个国家最好」因拒答理由含因果词而走了兜底）。

#### 建议升级优先级：v1.2 里两条现在挡在 Demo 主路径上

- **裸编号 vs 数据断言**：`23084` 这类纯数字商品编码被 V1 当成"没来源的数字断言"，
  商品类问题会被判不可信（HO-HARD-05）。实测：`销售额怎么样` 也因为模型写
  「974.77 万」被 V1 判"数字没有声明来源"——同属**单位换算**（HO-HARD-04）。
  这两条此前是按"holdout 上的误拦"登记的低优先任务，现在它们影响的是**正常问法的答案可信度**，
  建议提前到 P1-2 之后、M6 之前处理。

#### 建议执行顺序

M5 收口记录 → P0-1（时间窗）→ P0-2（口径声明）→ P1-1（模板 + 集中度）→ P1-2（能力卡）→ M6 项目收口报告。
