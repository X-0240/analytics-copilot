## 三、修掉一个测试污染（本轮发现，含我自己的一个错）

**现象**：service 测试把请求写进了仓库的 `logs/usage.jsonl`（252 行测试记录），
而 `/metrics` 的今日成本正是从该文件回填的——**测试噪声会被算成真实花费**
（容器首次启动就显示 `cost_cny_today = 2.0`）。

**修法**：在既有的 `tests/conftest.py`（M0 起就有 `src` 路径引导）里新增一个
autouse 夹具，把 `LOG_DIR` / `USAGE_LOG` 重定向到临时目录。
**验证**：跑测试前后 `logs/usage.jsonl` 行数 `253 → 253`。
被污染的旧日志改名为 `logs/usage.jsonl.pretest-backup-20261012`（保留未删）。

**期间我自己踩的坑**：改写 `conftest.py` 时把原有的 `src` 路径引导整段删掉了，
导致全部测试 `ModuleNotFoundError`。根因是"以为这文件是我新建的"，
没先 `git log -- tests/conftest.py` 确认它的来历。已恢复，并写成幂等插入。
教训：**改一个我没确认过来历的文件之前，先查它在版本库里的历史**。

## 四、容器化实测（真实执行，非推断）

```bash
docker build -t analytics-copilot:m5-1 .
```

## 五、Docker Desktop 环境故障的排查（非项目代码问题）

1. 10-11 两次启动后 `docker info` 都失败（pipe 不存在）；查到
   `%LOCALAPPDATA%\Docker\backend.error.json`（10-08 留下）显示 **Secrets Engine 初始化失败**：
   把 `engine.sock` 重命名为 `.stale` 时报 1920（The file cannot be accessed by the system）。
2. `engine.sock` 属性为 `Archive + ReparsePoint + Encrypted`（EFS）。
   `fsutil reparsepoint delete`、`Move-Item`、`cipher /d` 全部失败（1920 / 拒绝访问）；
   结论：那是**陈旧且不可访问的残影文件**，本机权限层动不了它。
   容器内也看不到该文件，无法代为删除。
3. 10-12 重新启动 Docker Desktop 并**多等了一会儿**（此前只等约 60 秒）→ 引擎就绪
   （Server 29.8.0），`backend.error.json` 自行消失；旧 `engine.sock` 仍在，但不再阻塞启动。
   **结论：上次没起来是等待不足 + 陈旧文件叠加，没有做任何系统级清理、没有重装。**
4. **一次误判，已纠正**：排查时我用 `New-Item` 在
   `%LOCALAPPDATA%\docker-secrets-engine\` 下建过一个 0 字节测试文件，
   随后一直以为它落在真实磁盘上、需要手动删除（因为我在沙箱里删不掉）。
   两次让用户手动删除都报"路径不存在"，于是换**沙箱外**的视角复核：

   ```
   docker run --rm -v "%LOCALAPPDATA%\docker-secrets-engine:/mnt/s:ro" \
     analytics-copilot:m5-1 sh -c "ls -la /mnt/s; test -e /mnt/s/codex-write-test.txt && echo EXISTS || echo NOT_FOUND"
   → 只有 engine.sock；NOT_FOUND
   ```

   结论：那个文件**只存在于我这边的沙箱视图**——该目录的 ACL 只给沙箱身份 `RX`，
   我的写入被重定向到了沙箱侧，真实磁盘上从未出现。**用户无需做任何清理。**
   （同一次复核也确认：仓库改动与 Downloads 里的台账写入都落在真实磁盘上。）

   教训：**跨权限边界判断"文件是否存在"时，不能只用自己进程的视角**；
   可以用一个跑在边界之外的中立观察者（这里是 Docker 守护进程侧的挂载视图）交叉验证。

## 九、兜底回答的可用性修订（2026-10-12，用户手机实测反馈）

### 9.1 现象（用户反馈）

手机问「最近三个月为什么销售额下降，按国家」时，页面上只有一句
`本次只做事实与相关变化描述：最大维度是 United Kingdom（值 8187806.36）`，
边界说明压过了信息量——**降级回答只说"我不能做什么"，没有把已经查到的结果讲清楚，
也没告诉用户下一步能问什么**。

### 9.2 根因（两条，机制层面查实）

1. **兜底只取一格结果**：`_causal_fallback` 只用"维度贡献"的第一行拼一句话，
   而趋势结果、维度占比这些已经执行完的数据没被组织成结论；
   兜底路径还**绕过了验证层**（claims 为空），等于免检。
2. **口径没写明白**：`understanding.time_window` 对「最近三个月」只解析出「最近」，
   而且 `plan()` **完全没用时间窗**（规则计划的 SQL 没有时间过滤）。
   所以那句 UK 8187806.36 是**全期**数字，用户问的却是"最近三个月"——
   数字没错，**口径没对上，且没有声明**。

### 9.3 本轮改了什么

| 改动 | 内容 |
|---|---|
| 事实化 | 兜底改为从结果行机械生成 2 条事实：①按月趋势（首/末/最低/最高月）②占比最高的三个维度；数字逐字取自结果并声明来源步骤 |
| 走验证层 | 兜底结论进同一套 V1/V2/V3/V4，`verification.status` 如实返回（此前是"免检"） |
| 口径声明 | 显式写出"以上为全期汇总，规则计划当前不按最近 N 个月过滤时间窗" |
| 末月提醒 | 数据集最后一个月只到 `2011-12-09`，属不完整月；命中时自动加提醒，避免把 12 月的低值读成暴跌 |
| 下一步 | 返回 `next_questions`（确定性模板，不调模型），页面渲染成"可以继续问" |

改后同一条问题的输出（走公网 URL 实测）：

```
销售额按月汇总：从 2010-12 的 748957.02 到 2011-12 的 433668.01，
其间最低 2011-12（433668.01）、最高 2011-11（1461756.25）；
占比最高的三个维度：United Kingdom（8187806.36，占 84.0%）、
Netherlands（284661.54，占 2.9%）、EIRE（263276.82，占 2.7%）
```

### 9.5 本轮暴露、但**没有**顺手改的东西（待决策）

1. **规则计划忽略时间窗**（`plan()` 不按 `understanding.time_window` 过滤）。
   这不是展示问题而是口径问题：「最近三个月」拿到全期数字。
   为什么没顺手修：需要先把"N 个月"解析成日期区间，而且**对比类问题**（如
   「最近哪个国家销售额下降最多」）若一律按最近 N 月过滤会答错——两者要一起设计。
   本轮只做到"如实声明口径"。
2. **末月不完整**对 LLM 路径（正常回答）同样存在，但只在兜底路径加了提醒；
   正常路径要修得进验证层（V3 之外再加一条数据口径检查）。
3. 兜底触发条件依赖"模型拒答理由里出现因果词"，措辞不同就会掉回普通拒答
   （本轮 T-203「哪个国家最好」因为拒答理由含因果词而走了兜底）。
