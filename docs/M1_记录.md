# M1 记录：受控 LLM 规划链路（2026-10-11）

## 一、目标与边界

目标：**验证受控 LLM 规划链路**，不是扩功能。API 与查询接口保持 M0 形状（只增字段），
状态谓词作为**执行前检查**保留；未做多 Agent、未扩分析类型、未部署、未改 M0 护栏。

## 二、已完成事实

| 项 | 事实 |
|---|---|
| 规划器 | `planner.py`：LLM 出 `{scope, assumptions, steps[{name,purpose,sql}]}`；结构校验 → 每步 SQL 过 M0 护栏 → 步数上限 4 → **失败只允许一次修复重试** |
| 结论器 | LLM 基于**已执行结果**写结论，**必须引用真实存在的步骤编号**，编造编号即判无效 |
| 双路径 | 无 key/桩 → 规则路径（M0 行为，回归测试不变）；有 key → LLM 路径；两条路径共用同一套谓词与护栏 |
| 能力边界 | 预测 / 因果 / 利润等词命中即**拒答**并给原因（机械可判，两条路径一致） |
| 评测 | `eval/tasks/m1_tasks.json`：12 正常 + 3 澄清 + 3 拒答；runner 会模拟澄清对话（≤2 轮后带假设继续） |
| 验证 | `pytest` **28 passed**；`ruff` 通过 |

## 三、验收结果（真实模型 deepseek-flash，2026-10-11）

运行：18 题、耗时 47 秒、成本 **0.063222 元**（两次调用/题：计划 + 结论）。

| 验收项 | 要求 | 实际 | 结论 |
|---|---|---|---|
| 正常分析案例 | ≥8 | **10/12** | 通过 |
| 澄清/拒答案例 | ≥4 | **6/6** | 通过 |
| 拒答正确性 | 预测/因果/利润各 1 | **3/3** | 通过 |
| 结果含计划/查询/证据链/结论 | 每例 | 13/18 全含；其余为拒答或失败 | 部分 |
| 失败与限制记录 | 必须有 | 见下 | 完成 |

澄清行为（谓词放宽后）：多数正常问题 **0 轮澄清**直接回答；
只有表述确实缺信息的（T-106 平均单价、T-110 拆分口径）才问 2 轮。

## 四、失败案例（真实记录，不隐藏）

1. **T-112 计划两次都撞护栏 → 整题记 error**（`SqlRejected`）。
   护栏生效是好事，但**行为不对**：两次修不好应当**降级为"无法完成 + 原因"**，
   而不是把任务判成异常。→ 待改（M2 与验证层一起做）。
2. **T-107 有步骤返回 0 行，证据链被判不完整**（计划 3 步、有证据 0 步）。
   空结果没有被标注成问题 → 待改：**零行结果必须进 caveats**。
3. **T-203（设计为"澄清"）被模型拒答**：模型认为"最好"含义不明、可能涉及利润/预测。
   这本身是**合理行为**（拒绝猜），但说明"澄清 vs 拒答"在执行时有重叠，
   评测把两者都算作边界正确（已按此口径实现）。
4. **首轮 6 例失败**（修复前）：4 例是 `db.SqlRejected` 逃出了重试循环（模型写错 SQL 一次即整题失败）；
   2 例是 DuckDB 的 `Decimal` 无法 JSON 序列化（`TypeError`）。两者都已修：
   重试循环改为也捕获护栏异常；数据层统一做 JSON 归一化。

## 五、限制

- 规则路径的谓词口径仍偏"问得多"（缺指标必问）；放宽后已明显减少；
- LLM 规划质量受模型影响，**同一问题两次运行的结论可能不同**（未做一致性检查，属 M3）；
- 结论正确性（是否被数据支持）**仍未评测**——M1 只保证"有证据链"，不保证"证据支持结论"；
- 步数上限 4 是拍的工程值，未做敏感性实验。

## 六、下一步最小验证产出（M2）

1. 把"两次修不好"降级为结构化失败（`PLAN_UNREPAIRABLE` → 返回无法完成 + 原因）；
2. 零行结果进 caveats；
3. 上验证层第一版（机械可判）：结论数字与查询结果是否一致、是否存在更大量级被忽略因素；
4. 产出：无验证层 vs 有验证层 的第一组对照数字（M4 才做完整对照）。
